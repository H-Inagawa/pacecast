# 要件定義

作成日: 2026-09-06  
根拠: `docs/00_concept/initial-request.md`

## 1. 背景と目的

ランニングのパフォーマンスは気温・湿度などの気象条件で変化する。PaceCast は、過去の走行記録と気象データを蓄積し、未来の気象条件でどの程度のパフォーマンスが期待できるかを示す。

本プロジェクトはアプリケーション完成に加え、要件整理からテストまでの開発プロセスを学ぶことも目的とする。

## 2. 利用者

初期は開発者本人。入場はメール＋パスワード。走行・設定はログイン中のアカウント単位。開発者は固定アカウントで登録なしに入れる。

## 3. 機能要件

### FR-1 気象データの取得

- 走行の保存時に、指定地点の過去気象を自動取得すること
- 直近数日はアメダス map JSON、それより前は Open-Meteo 再解析を使うこと
- 地点名、観測日時、気温、湿度、風速、日射、推定 WBGT を保持すること
- 同じ観測日時・地点は上書き（再取得可能）であること
- 欠測（気温または湿度が空）の行はスキップすること

### FR-2 ランニング記録の登録

- 走行日時、走行距離（km）、走行時間、平均心拍数を登録できること
- 記録追加の初期地点は、設定どおりのアメダスか GPS 最寄りかを選べること。GPS 不許可でも記録は追加できること
- 平均心拍数は任意項目であること
- 登録済み記録の一覧・編集・削除ができること
- 走行時間からペース（分秒/km）を算出して表示すること
- 一覧の各行にペースと、気象（気温・湿度・WBGT）を別列で出せること。未関連は `--.-℃` / `--%` / `--.-`。WBGT列ヘッダに説明を出せること
- 一覧の表示列は選べること。日時と距離は必須。気象の各項目も個別に選べること。下部は「表示項目設定」「記録を追加」「ホームへ戻る」を 1:3:1 にすること
- 一覧の行色は設定で心拍 / 気象（WBGT） / しないを選べること。気象色分けのとき、未関連と WBGT 無しはグレーにすること

### FR-3 気象と記録の関連付け

- 走行開始日時に最も近い気象観測（1時間値）を自動で関連付けること。走行が別の1時間値にまたがるときは、終了時刻の最近傍も取り、気温・湿度・風・日射を平均して推定 WBGT を付け直すこと。同じ1時間値に収まる短い走は開始の1点のままでよいこと
- 該当する観測が無い場合は未関連のまま保存し、一覧では `--.-℃ / --%` と出すこと
- 予測・グラフなど気象条件を使う計算では、未関連の走行記録と、推定 WBGT が無い走行記録を対象にしないこと
- 気象を再取得したあと、未関連の記録を再関連付けできること

### FR-4 パフォーマンス予測

指定した気象条件に対して、次を算出・表示すること。

- 予想走行ペース（分秒/km）
- 指定距離に対する予想タイム

予想平均心拍数は結果に出さない。心拍は走行強度（目標 bpm）の指定と、式モデルの説明変数に使う。

予測は直近ほど重い重み付き最小二乗の式モデル。結果に RMSE（秒/km）と R²、WBGT / 心拍 / 距離とペースの関係グラフを出す。タイトル横で方法と妥当性の基準を説明する。

気象条件の与え方は次の2通りとする。

1. 気温・湿度の手動入力（送信時に風・日射を足して推定 WBGT を計算）
2. 日時指定（天気予報からその時刻の気温・湿度・風・日射を取得し、推定 WBGT を計算）

根拠表には予測対象との推定 WBGT 差と、学習に使った新しい過去走を出す。信頼度（高 / 中 / 低）は R² から決める。

Web ブラウザから、走行記録の CRUD、予測実行、ランニング天気予報（3日。現在の気象と走りやすさ予報。時刻を縦にした表。WBGT(体感)のセルだけ色分け。説明は「走りやすさとは？」。グラフは出さない）、周回コースの提案、設定ができること。分析用の専用画面は置かない（WBGT とペースは予測の関係グラフで見る）。コースは保存しない。OpenStreetMap の歩道・歩道付き道路・歩行者／自転車通行可の道・公園内通路・河川敷経路をつないだネットワークをたどり、同じ向きの曲がりを優先し（ロリポップ型より周回を拾いやすくする）、公園の縁や堀・河川沿いの道はごく弱く優遇し、出発直後は分岐を絞り込まず探し（距離が長いほどその区間を短くする。基準は約800m）、時計回りに戻る周回を距離に応じた上限（長いほど少なく。最大50件）まで集め、打ち切り件数に達したら探索をやめ、点数の高い順に最大5件出す。幹線道路本体は歩道タグが無い限り採用しない。独立した専用歩道（`highway=footway` かつ `footway=sidewalk`）はルートに使わず、それと並ぶ歩道タグのない車道を走りやすい道として扱う。少し行ってすぐ戻る短い突き出しや、車線乗り換えのような短い折れはまっすぐな道に直す。直前の道を180度引き返すUターンはしない。同じ道を周回のあとで再利用して戻るのは許す。走りやすい道だけで閉じないときは、生活道路などの歩行可能な接続道路を足す（長い利用は細い道の点数で下げる）。スタートは、面している細い道や公園内の通路を含む、いちばん近い走りやすい道または接続道路から始める。広場や山奥など、近くにスタートできる道が無いときは、理由と起点の移動案内を出す。追加探索は距離が長いほど減らし、17km以上は足さない。出発した向きの逆も探す。公園内の通路は、園内の半分以上を通っていれば走りやすい道として周回に入れる。円・正方形・長方形の概形は先に置かない。表示は向きが重ならない候補を点数の高い順に最大5件。除外は指定の±20%の外、道路重複10%超、または細い道40%超。出発点から周回までの同じ道は、その先で分かれて周回になるなら重複に数えない。合格が無いときは、距離が最も近い案と、距離は合って重複が多い案を1件ずつ表示し、起点周辺の走りやすい道を細い青線で示して起点の移動を案内する。通常の結果では走りやすい道の青線は出さない。計画中・建設中・廃止・撤去・未使用の道路は検索から除外する。エラー時はメッセージへ、成功時は地図へ自動スクロールする。採点表の各項目は取得点と満点を並べる。点数は指定距離との差（20点）、走りやすい道の割合（20点）、細い道の短さ（20点。全距離の25%で0点、40%超は除外）、直進（10点）、信号（10点。実距離1kmあたり5回で0点。`crossing=traffic_signals` など信号付き横断）、曲がり角（10点。1kmあたり1か所以下で満点、3か所で0点）、道路重複（10点。10%で0点）。配点の合計は100点。交差点・上り・下り・時計回り・Uターンは点数に入れず表にも出さない。曲がってすぐ元の道へ戻る短い往復は、まっすぐな道に直してから距離と重複を見る。地図の下の表に、おすすめ度・スコア・距離と内訳を出す。コース名のボタンで地図の線を切り替える。評価はその回の最高実スコアを100点にした相対評価で、実スコアは素点。カッコ内は実スコア。表の右上に採点基準を置く。予想ペースと予想タイムは出さない。作り方は「作成方法」に出す。作成に数分かかることがある旨を画面に出す。検索中はスピナーの下に、経路を聞けた割合と除外を通った件数を出し、「検索を中止」で止められる。画面間の移動はヘッダ左のドロワーでもできること。未ログインではログイン画面へ誘導し、新規登録は Gmail SMTP で送る確認リンクのあと、ユーザー名・アメダス地点・誕生日を入れて完了すること。パスワードを忘れたときは同じ SMTP で再設定リンクを送ること。SMTP 未設定のローカルでは画面上のリンクでも確認・再設定できること。

## 4. 非機能要件

- ローカルで起動・利用できること（初期は個人利用）
- データは Supabase PostgreSQL に永続化すること（pytest 用に SQLite も残す）
- 予測ロジックは説明可能であること（初期は統計、機械学習は将来）

## 5. 気象データの出典

手動 CSV は使わない。過去観測はアメダス map JSON と Open-Meteo 再解析、予報は Open-Meteo。
